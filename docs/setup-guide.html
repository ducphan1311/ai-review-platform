Hướng Dẫn Thiết Lập Hệ Thống & Tích Hợp CI/CD

Tài liệu đặc tả quy trình triển khai On-Premise container, kích hoạt bản quyền Ed25519, tích hợp Webhook cho GitHub/GitLab Monorepo và quản lý nợ kỹ thuật bằng baseline.

1 Yêu Cầu Hạ Tầng (Prerequisites)

  • Hệ điều hành: Linux (Ubuntu 20.04+, RHEL 8+, Debian 11+) hoặc macOS / Windows WSL2.
  • Container Runtime: Docker Engine 24.0+ hoặc Podman / Kubernetes.
  • Tài nguyên tối thiểu: 2 vCPU, 2GB RAM, 10GB dung lượng ổ đĩa.
  • Mạng: Cho phép server GitHub/GitLab gửi HTTP POST Webhook tới port 8080 của container.
  • LLM Backend: Cung cấp OpenAI API Key hoặc bất kỳ OpenAI-compatible endpoint nào (Local Ollama, vLLM, Azure OpenAI).

2 Khởi Chạy Docker Container On-Premise

Mount file license.lic do Danny cấp vào container. Nếu license hết hạn hoặc bị giả mạo, server sẽ từ chối khởi động để đảm bảo an toàn. 

# 1. Tạo thư mục làm việc và đặt file license.lic vào
mkdir -p /opt/ai-review
cp /path/to/downloaded/license.lic /opt/ai-review/license.lic

# 2. Khởi chạy Docker Container
docker run -d \
  --name ai-review-service \
  --restart unless-stopped \
  -p 8080:8080 \
  -v /opt/ai-review/license.lic:/app/license.lic:ro \
  -e GITHUB_WEBHOOK_SECRET="your-secret-hex-chars" \
  -e OPENAI_API_KEY="sk-proj-***" \
  -e OPENAI_BASE_URL="https://api.openai.com/v1" \
  -e AI_REVIEW_MODEL="gpt-4o" \
  ducphan1311/ai-review-platform:latest

Hướng Dẫn Cấu Hình Webhook Trong Mạng LAN Nội Bộ (GitLab / GitHub Enterprise)

Khi máy chủ Git Server và máy chủ chạy Docker Container cùng nằm chung dải mạng Private LAN (ví dụ 10.0.x.x hoặc 192.168.x.x), toàn bộ dữ liệu di chuyển 100% nội bộ không cần Internet.

⚠️ Lưu Ý Quan Trọng Cho GitLab On-Premise (SSRF Protection):

Mặc định, GitLab sẽ chặn Webhook gửi tới các địa chỉ IP nội bộ và báo lỗi: Requests to localhost/local network are not allowed. Bạn cần bật quyền theo các bước sau:

  1. Truy cập GitLab với quyền Admin: Admin Area → Settings → Network
  2. Mở rộng mục Outbound requests
  3. Tick chọn: Allow requests to the local network from webhooks and integrations
  4. Bấm Save changes để áp dụng.

Điền thông số Webhook trên GitLab / GitHub Repository:

# 1. URL máy chủ container On-Premise:
URL: http://10.0.12.34:8080/
# 2. Secret Token (khớp với GITHUB_WEBHOOK_SECRET khi chạy docker run):
Secret Token: your-super-secret-token-32-chars-min
# 3. Trigger Events (Sự kiện kích hoạt):
Triggers: [x] Merge request events (GitLab) hoặc [x] Pull requests (GitHub)

Kết Nối GitHub.com Về Server Nội Bộ Bằng Cloudflare Tunnel (Zero Open Ports)

Nếu công ty của bạn dùng GitHub.com (Cloud) nhưng máy chủ quét AI nằm sau tường lửa công ty và bị cấm mở port / cấm NAT IP tĩnh, giải pháp an toàn nhất đạt chuẩn ngân hàng là sử dụng Cloudflare Tunnel.

🛡️ Lợi Ích An Ninh Tuyệt Đối:
  • Không cần mở bất kỳ cổng Inbound nào trên Router Firewall (No Port Forward).
  • Tự động kích hoạt mã hóa SSL/TLS chuẩn Cloudflare Edge.
  • Chống tấn công DDoS và kiểm soát lượng request.
⚡ Cách Hoạt Động:

Container cloudflared tạo 1 outbound tunnel an toàn ra Cloudflare Edge. Khi GitHub bắn webhook vào domain, Cloudflare đẩy về port 8080 nội bộ.

Chạy Cloudflare Tunnel bằng 1 câu lệnh Docker duy nhất trên cùng máy chủ:

# 1. Khởi chạy Cloudflare Tunnel Client kết nối về Cloudflare Zero Trust:
docker run -d   --name ai-review-tunnel   --restart unless-stopped   --network="host"   cloudflare/cloudflared:latest tunnel --no-autoupdate run --token <YOUR_CLOUDFLARE_TUNNEL_TOKEN>

# 2. Cấu hình trên Dashboard Cloudflare Zero Trust:
# Public Hostname: ai-review.yourdomain.com -> Service: HTTP -> localhost:8080

# 3. Trên GitHub.com -> Repo Settings -> Webhooks:
# Payload URL: https://ai-review.yourdomain.com/
# Content type: application/json

Phương Án C: Chạy Trực Tiếp Trong CI Pipeline (Self-Hosted CI Runner)

Dành cho môi trường cô lập tuyệt đối (Air-Gapped / Inbound bị chặn 100%), không muốn duy trì Webhook server thường trực. Pipeline sẽ kích hoạt container quét trực tiếp theo từng PR/MR.

name: Architecture & AI Review Quality Gate

on:
  pull_request:
    branches: [ main, develop ]
    types: [ opened, synchronize, reopened ]

jobs:
  architecture-gate:
    name: Deterministic AST & AI Advisory Gate
    # Chạy trên self-hosted runner nội bộ (không cần mở cổng mạng ra ngoài)
    runs-on: self-hosted

    steps:
      # 1. Checkout mã nguồn repo với đầy đủ git history để so sánh delta diff
      - name: Checkout Code Repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0 # Bắt buộc lấy toàn bộ commit history để so sánh với nhánh đích

      # 2. Khởi chạy container quét mã nguồn & thực thi Quality Gate
      - name: Run Commercial Architecture & Quality Gate
        env:
          # Cấu hình LLM nội bộ (100% On-premise, không gửi code ra bên ngoài)
          OPENAI_BASE_URL: "http://ollama-internal:11434/v1"
          OPENAI_API_KEY: "internal-key-placeholder"
          AI_REVIEW_MODEL: "qwen2.5-coder:32b"
        run: |
          echo "🚀 Đang kích hoạt engine kiểm tra kiến trúc On-Premise..."

          # Lệnh chạy container kiểm tra trực tiếp mã nguồn được mount vào /repo:
          # -v $(pwd):/repo: Mount thư mục code hiện tại vào container
          # -v /opt/ai-review/license.lic:/app/license.lic:ro: Mount file bản quyền bảo mật
          docker run --rm             -v $(pwd):/repo             -v /opt/ai-review/license.lic:/app/license.lic:ro             -e OPENAI_BASE_URL="${OPENAI_BASE_URL}"             -e OPENAI_API_KEY="${OPENAI_API_KEY}"             -e AI_REVIEW_MODEL="${AI_REVIEW_MODEL}"             ducphan1311/ai-review-platform:latest             python -m app.arch_engine.cli check               --repo-path /repo               --config /repo/config/architecture_rules.yaml               --baseline /repo/baseline.json               --diff               --base origin/${{ github.base_ref }}               --format terminal

      # Giải thích từng dòng cờ lệnh (Arguments):
      # --repo-path /repo: Đường dẫn thư mục mã nguồn cần quét
      # --config ...: File quy tắc kiến trúc (phân tầng, cấm import vòng)
      # --baseline ...: Nợ kỹ thuật cũ được ghi nhận (nguyên lý Clean-As-You-Code)
      # --diff: Chỉ phân tích các file bị chỉnh sửa trong PR này (tiết kiệm thời gian)
      # --base: Nhánh cơ sở để diff (ví dụ origin/main)
# .gitlab-ci.yml - Cấu hình kiểm tra kiến trúc trên GitLab On-Premise

stages:
  - quality-gate

ai-architecture-review:
  stage: quality-gate
  # Gán tag cho runner nội bộ của công ty (Docker executor hoặc Shell executor)
  tags:
    - internal-docker-runner
  only:
    - merge_requests

  variables:
    # Không gửi dữ liệu ra ngoài Internet - trỏ về cụm AI Server nội bộ
    OPENAI_BASE_URL: "http://ollama-internal:11434/v1"
    OPENAI_API_KEY: "internal-key-placeholder"
    AI_REVIEW_MODEL: "qwen2.5-coder:32b"

  script:
    - echo "🔍 Bắt đầu quét kiểm tra kiến trúc Merge Request trên GitLab..."
    # Lấy thông tin nhánh đích để so sánh sai khác (Git diff)
    - git fetch origin $CI_MERGE_REQUEST_TARGET_BRANCH_NAME
    # Chạy container phân tích kiến trúc
    - |
      docker run --rm         -v $(pwd):/repo         -v /opt/ai-review/license.lic:/app/license.lic:ro         -e OPENAI_BASE_URL="${OPENAI_BASE_URL}"         -e OPENAI_API_KEY="${OPENAI_API_KEY}"         -e AI_REVIEW_MODEL="${AI_REVIEW_MODEL}"         ducphan1311/ai-review-platform:latest         python -m app.arch_engine.cli check           --repo-path /repo           --config /repo/config/architecture_rules.yaml           --baseline /repo/baseline.json           --diff           --base origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME           --format terminal

  # Nếu có vi phạm mới (BLOCKER), CI Pipeline sẽ FAILED ngay lập tức để bảo vệ nhánh chính
  allow_failure: false
🔒 100% On-Premise LLM: Nếu chính sách doanh nghiệp cấm kết nối ra OpenAI, truyền biến OPENAI_BASE_URL="http://ollama-internal:11434/v1" và AI_REVIEW_MODEL="qwen2.5-coder:32b" để xử lý AI hoàn toàn offline!

3 Cấu Hình Tệp Quy Tắc architecture_rules.yaml

Tại thư mục gốc của repository cần kiểm tra, tạo thư mục config/ và đặt file architecture_rules.yaml: 

version: "1.0.0"
monorepo:
  package_dirs: ["lib"] # Chỉ định thư mục mã nguồn

# 1. Định nghĩa phân tầng Clean Architecture
layers:
  - name: "domain"
    aliases: ["config", "utils", "core"]
    description: "Tầng logic nghiệp vụ & entity cốt lõi"
  - name: "presentation"
    aliases: ["pages", "widgets", "ui"]
    description: "Tầng giao diện người dùng"
  - name: "data"
    aliases: ["datasources", "repository", "network"]
    description: "Tầng dữ liệu DB & API"

# 2. Quy tắc kiểm soát nghiêm ngặt
rules:
  - id: "RULE_CLEAN_DOMAIN"
    type: "layer_boundary"
    source_layer: "domain"
    forbidden_target_layers: ["presentation", "data"]
    severity: "BLOCKER"

  - id: "BAN_PRINT_ON_PROD"
    type: "forbidden_calls"
    calls: ["print", "debugPrint"]
    severity: "BLOCKER"

  - id: "RULE_CIRCULAR_DEP"
    type: "layer_boundary"
    severity: "BLOCKER"

4 Cơ Chế Baseline Quản Lý Nợ Kỹ Thuật (Clean-As-You-Code)

Triết lý Clean-As-You-Code giải quyết bài toán nhức nhối nhất khi áp dụng bộ luật kiểm soát kiến trúc vào các dự án lâu năm (Legacy Codebase): "Dự án đã có sẵn hàng trăm lỗi kiến trúc cũ, làm sao bật Quality Gate mà không làm tê liệt tiến độ release của toàn bộ các team?"

🎯 1. Khoanh Vùng Nợ Cũ

Toàn bộ vi phạm hiện có sẽ được đóng băng (freeze) vào file baseline.json và được gán nhãn là "nợ kỹ thuật đã chấp nhận".

🛡️ 2. Chặn Đứng Vi Phạm Mới

Mọi Pull Request mới từ nay chỉ bị FAILED nếu nhà phát triển vô tình tạo ra vi phạm MỚI so với baseline.

📉 3. Tự Động Giảm Nợ Dần

Khi dev refactor và sửa bớt lỗi cũ trong PR, baseline sẽ tự động co lại. Nợ kiến trúc giảm dần theo thời gian mà không cần dừng dự án.

Quy Trình 3 Bước Tạo Và Đưa Baseline Vào Vận Hành Thực Tế:

Bước 1

Tạo file snapshot baseline cho toàn bộ mã nguồn hiện tại

Chạy lệnh CLI sau từ máy của Tech Lead / DevOps hoặc trực tiếp trên server qua container:

# Cách 1: Sử dụng Docker Container trực tiếp trong thư mục repository:
docker run --rm -v $(pwd):/repo ducphan1311/ai-review-platform:latest   python -m app.arch_engine.cli baseline /repo   --config /repo/config/architecture_rules.yaml   --output /repo/baseline.json

# Hoặc Cách 2: Nếu container đang chạy dưới dạng background service:
docker exec ai-review-service python -m app.arch_engine.cli baseline /path/to/repo   --config config/architecture_rules.yaml   --output baseline.json
Bước 2

Kiểm tra cấu trúc và Commit file baseline.json lên nhánh chính (main)

File baseline.json sinh ra có định dạng chuẩn mực chứa mã băm xác thực (SHA-256 Signature) cho từng lỗi, không phụ thuộc vào dòng code hay timestamp (Deterministic):

{
  "version": "2.0.0",
  "total_violations_recorded": 14,
  "violations": [
    {
      "signature": "a7b3c9d1e2f4a5b6",
      "file_path": "lib/domain/usecases/login_usecase.dart",
      "rule_id": "RULE_CLEAN_DOMAIN",
      "import_statement": "import 'package:app/data/datasources/api.dart';",
      "first_detected_at": "accepted-baseline"
    }
  ]
}

Commit file này vào Git để làm mốc tham chiếu chuẩn cho toàn bộ team:

git add baseline.json && git commit -m "chore(arch): initialize clean-as-you-code baseline" && git push origin main
Bước 3

Cách Engine sử dụng file baseline.json trong các lần quét PR tiếp theo

Trong mọi lần quét PR (cả qua Webhook lẫn CI Pipeline), cờ --baseline baseline.json sẽ kích hoạt bộ lọc BaselineManager.filter_violations():

✅ Vi phạm cũ (Có trong baseline.json):

Được đánh dấu is_new: false. Engine bỏ qua và CHO PHÉP PASS, không làm chặn tiến độ release.

❌ Vi phạm mới (Không có trong baseline.json):

Được đánh dấu is_new: true. Engine báo FAILED (Exit code 1) và kích hoạt AI tư vấn giải pháp sửa ngay.

🔄 Khi nào cần Re-baseline (Tái tạo lại baseline)?

Khi dự án cập nhật thêm các quy tắc mới trong architecture_rules.yaml hoặc khi nhóm kỹ thuật đã hoàn tất một đợt dọn dẹp kỹ thuật lớn (Refactoring sprint), chỉ cần chạy lại lệnh ở Bước 1 để cập nhật file baseline.json mới nhất.
